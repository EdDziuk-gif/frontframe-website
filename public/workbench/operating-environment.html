1 · Repo layout — verify before touching anything

One GitHub repo, two deployables.

frontframe-site/                       ← GitHub repo root (EdDziuk-gif/frontframe-website)
├── public/                            ← Cloudflare Pages serves this. Deploys via git push.
│   └── admin.html, index.html, etc.
├── functions/                         ← Cloudflare Pages Functions (password gate middleware)
└── worker/                            ← Cloudflare Worker, api.frontframe.co. NOT a separate
    ├── wrangler.jsonc                    repo — tracked in this same git repo, but deployed
    ├── src/                              with a completely separate command. git push does
    │   ├── index.js                      NOT deploy the worker.
    │   ├── router.js
    │   ├── middleware/auth.js
    │   ├── routes/*.js
    │   └── shared/*.js
    └── test/router.contract.test.js

Older documentation describing the Worker as a separate frontframe-worker folder backed only by Time Machine is out of date. As of this reference, worker/ is a tracked subdirectory of frontframe-site, pushed to the same GitHub remote.

cd ~/Development_Assets/FrontFrame_Website_CoWork/frontframe-site
git ls-files worker | head
git remote -v

If a future session finds a genuinely separate frontframe-worker folder, stop and flag the conflict rather than guessing which copy is current.

2 · Deploying — two independent commands

Site: public/ and functions/

Cloudflare Pages deploys from git. Use the repository script rather than raw add/commit/push.

cd ~/Development_Assets/FrontFrame_Website_CoWork/frontframe-site
./deploy.sh "Description of change"

deploy.sh removes a stale .git/HEAD.lock if present, verifies the working copy, stages, commits, and pushes. Cloudflare Pages then auto-builds. After 1–2 minutes, verify production with a unique string from the change.

curl -s https://frontframe.co/admin | grep "<some unique string from your change>"

Worker: worker/

The Worker deploy is completely separate from git push.

cd ~/Development_Assets/FrontFrame_Website_CoWork/frontframe-site/worker
npx wrangler deploy --config wrangler.jsonc

Git push does not deploy the Worker. Worker changes must both be deployed with Wrangler and committed/pushed so production and the repo do not silently drift apart.

Do not use --no-bundle

The historic --no-bundle command currently causes a Wrangler module-resolution failure on this project. Dry-run inspection showed only index.js being written with the flag, versus a complete ~110KB bundle without it. Deploy without --no-bundle until the underlying Cloudflare issue is root-caused.

3 · Git hooks — expected behavior

  • Commit subject ≤ 72 characters. Use a short first -m and a second -m for the body when needed.
  • Interactive commit messages require a blank line after the subject. Supplying -m is more reliable in terminal sessions where the editor may misbehave.
  • Worker changes run tests automatically. Staging anything under worker/ triggers Vitest; a failing test blocks the commit.
  • New files without matching tests may prompt for YES; this is a reminder rather than a test gate.
  • Push-time messages are reminders. Public changes announce the Pages build; Worker changes remind you that push does not deploy the Worker.
git commit -m "Short subject under 72 chars" -m "Longer explanation goes here."

4 · Diagnosing git problems — verify before assuming corruption

  1. fatal: bad object <sha>: run git fetch origin, then git fsck --full. Dangling objects are ordinary debris; missing or broken objects are the real problem.
  2. main -> main (fetch first): local is behind remote. Inspect what changed, then merge explicitly with git pull --no-rebase origin main.
  3. Divergent branches warning: use --no-rebase for that pull rather than setting a global preference unless Ed requests one.
  4. Lock warnings from concurrent sessions: do not infer damage. Verify with git fsck --full; deploy.sh handles stale lock cleanup for its own runs.
git fetch origin
git fsck --full

git log <your-last-known-sha>..origin/main --stat
git pull --no-rebase origin main

5 · Terminal and editor quirks

  • If git commit cannot open vi, supply the commit message directly with -m.
  • If a pasted multi-line block gets stuck at a quote> prompt, press Ctrl+C, return to a normal prompt, and rerun commands one at a time.
  • Always confirm the working directory before destructive or deploy-related commands.
pwd

6 · Secrets and environment

The Anthropic API key is a Worker secret (env.ANTHROPIC_API_KEY), not a repo file. If chat reports an invalid API key, rotate the secret rather than changing code.

cd ~/Development_Assets/FrontFrame_Website_CoWork/frontframe-site/worker
npx wrangler secret put ANTHROPIC_API_KEY --config wrangler.jsonc

SUPABASE_URL is a non-secret var in wrangler.jsonc. SUPABASE_SERVICE_ROLE_KEY is also a Worker secret.

wrangler tail is the fastest path to the real runtime exception behind the visitor-facing generic error.

cd ~/Development_Assets/FrontFrame_Website_CoWork/frontframe-site/worker
npx wrangler tail

7 · General working rules

  • Read the file before editing it. Never edit from memory or an old copy.
  • Complete files only. No partial patches or “insert this somewhere” instructions.
  • grep for a unique string before staging to verify the edit landed in the intended file.
  • GitHub is the source of truth. Never deploy the site directly from the Cloudflare Pages dashboard.
  • Do not assume — verify. Repo location, Worker location, tracked state, schema constraints, and error meanings have all been wrong in prior assumptions and corrected by direct inspection.

Operational principle: one command that confirms a fact is preferable to a paragraph that assumes it.
